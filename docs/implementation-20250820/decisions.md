# 組織管理系統 - 設計決策記錄

## 1. 架構決策

### 1.1 資料模型設計
**決策**：使用擴充表方式，不修改既有 users 表
- **原因**：保持向後相容，不破壞現有功能
- **實作**：建立 user_extensions 表關聯既有使用者
- **影響**：需要 JOIN 查詢，但保護既有系統

### 1.2 部門樹狀結構
**決策**：使用 Materialized Path 模式
- **原因**：查詢效能佳，支援無限層級
- **實作**：parent_id + path 欄位
- **替代方案**：Nested Set（複雜）、Adjacency List（查詢慢）

### 1.3 認證架構
**決策**：支援多種認證方式並存
- **原因**：企業需求多樣化
- **實作**：auth_source 欄位區分，抽象層設計
- **考量**：SSO、LDAP、本地密碼可同時存在

## 2. 技術選型

### 2.1 密碼加密
**決策**：使用 bcrypt（rounds=12）
- **原因**：安全性高，抗暴力破解
- **替代**：Argon2（較新但支援度低）

### 2.2 SSO 整合
**決策**：優先支援 OAuth 2.0 和 Crowd
- **原因**：OAuth 是主流，Crowd 滿足特定需求
- **未來**：預留 SAML 2.0 擴充空間

### 2.3 同步引擎
**決策**：使用 APScheduler 做排程
- **原因**：Python 原生，輕量級
- **替代**：Celery（過度設計）、Cron（不夠彈性）

## 3. UI/UX 決策

### 3.1 頁面佈局
**決策**：延續現有設計系統
- **原因**：保持一致性，降低學習成本
- **實作**：使用既有 CSS 變數和元件

### 3.2 左側抽屜選單
**決策**：組織管理使用獨立抽屜
- **原因**：功能獨立，避免選單過長
- **實作**：可收合，記憶使用者偏好

### 3.3 批次操作
**決策**：提供精靈式介面
- **原因**：降低操作錯誤，提供即時回饋
- **步驟**：上傳→映射→預覽→執行→結果

## 4. 安全決策

### 4.1 密碼策略
**決策**：預設使用啟用連結
- **原因**：最安全，密碼不經手管理員
- **備選**：臨時密碼、LDAP 代理

### 4.2 審計日誌
**決策**：全面記錄，分區儲存
- **原因**：合規需求，效能考量
- **實作**：按月分區，自動歸檔

### 4.3 權限模型
**決策**：RBAC + 部門繼承
- **原因**：彈性且符合組織結構
- **實作**：角色定義功能權限，部門控制資料範圍

## 5. 效能決策

### 5.1 批次處理
**決策**：每批 100 筆
- **原因**：平衡記憶體和效能
- **可調整**：根據伺服器能力調整

### 5.2 快取策略
**決策**：Session 快取 5 分鐘
- **原因**：減少 SSO 伺服器負擔
- **實作**：Redis 或記憶體快取

### 5.3 資料庫索引
**決策**：預建常用查詢索引
- **原因**：提升查詢效能
- **索引**：user_id、department_id、created_at

## 6. 擴展性決策

### 6.1 系統模式
**決策**：支援基本/組織兩種模式
- **原因**：滿足不同規模需求
- **切換**：運行時可切換，資料保留

### 6.2 欄位映射
**決策**：JSON 配置 + UI 設定
- **原因**：簡單場景用 UI，複雜場景用 JSON
- **實作**：80/20 原則

### 6.3 同步來源
**決策**：支援多端點、多認證
- **原因**：企業 API 多樣化
- **實作**：抽象資料源介面

## 7. 待決策事項

### 7.1 國際化
- **問題**：是否支援多語言？
- **影響**：UI 文字、錯誤訊息
- **建議**：Phase 2 考慮

### 7.2 行動裝置
- **問題**：是否需要 APP？
- **現況**：響應式 Web
- **建議**：先優化 Web 體驗

### 7.3 資料備份
- **問題**：備份策略？
- **考量**：審計日誌、組織資料
- **建議**：每日增量、每週全量

## 8. 風險評估

### 8.1 技術風險
- **SSO 服務中斷**：需要備援機制
- **大量資料同步**：可能影響效能
- **密碼策略變更**：影響既有使用者

### 8.2 業務風險
- **部門重組**：需要批次調整功能
- **權限誤設**：需要審計和回滾
- **資料不一致**：需要同步驗證

## 9. 實作優先順序

### Phase 1（必要）
1. 基礎資料模型
2. 部門/角色/使用者 CRUD
3. 基本權限控制

### Phase 2（重要）
1. 密碼策略
2. 資料匯入
3. 系統模式切換

### Phase 3（進階）
1. SSO 整合
2. 自動同步
3. 審計系統
